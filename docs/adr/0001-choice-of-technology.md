# ADR-001: PostgreSQL як основне сховище та NetworkX для графових обчислень

**Status:** Approved (Затверджено)
**Обсяг рішення:** Backend API, один процес FastAPI.

### 1. Context — контекст

UseTrace Studio зберігає вимоги, ревізії та зв’язки трасуваності. Необхідно узгодити надійне зберігання з оперативною перевіркою DAG та аналізом впливу змін.

| Обмеження | Підстава |
| --- | --- |
| Відновлювана RAM-модель DAG, перевірка циклів алгоритмом Кана та аналіз впливу | [SRS-FUN-03](../srs.md#srs-fun-03)–05. |
| p95 повного топологічного впорядкування < 50 мс для 10000 вузлів і 30000 ребер | [SRS-NFR-PERF-02](../srs.md#srs-nfr-perf-02); завантаження з БД не входить у вимірювання. |
| p95 TTFB < 150 мс при 500 RPS | [SRS-NFR-PERF-01](../srs.md#srs-nfr-perf-01); окремий наскрізний профіль навантаження. |
| Один процес API; стенд 4 vCPU, 8 GiB RAM, SSD | Умови вимірювання SRS та поточні C4 Level 2–3. |

Основна дилема: виконувати графові операції в PostgreSQL, додати Neo4j або підтримувати похідну графову модель у пам’яті Python.

Поточна SRS уже передбачає DAG у RAM. Варіанти, що повністю замінюють цей механізм обчисленнями в СУБД, потребують погодженої зміни відповідних вимог. ADR документує обґрунтування прийнятого вибору.

### 2. Alternatives — альтернативи

| Варіант | Переваги | Обмеження та причина вибору / відхилення |
| --- | --- | --- |
| **PostgreSQL 16 + Recursive CTE** | Одне постійне сховище; SQL підтримує рекурсивні обходи та виявлення циклів [2]. | Вартість обходів залежить від запиту, індексів і структури даних. Варіант залишається придатною альтернативою, але змінює прийнятий спосіб RAM-обчислень. Універсальна складність O(V²) й фіксовані затримки йому не приписуються. |
| **PostgreSQL + Neo4j для графової проєкції** | Окрема графова модель і запити Cypher; обчислення можна винести за межі API. | Додає сервіс, мережеві виклики, моніторинг і синхронізацію двох сховищ. Пам’ять Neo4j потрібно підбирати під конкретні дані й запити [4]. Для поточного обсягу потреба в додатковій СУБД не доведена. |
| **PostgreSQL + NetworkX у процесі API** | Зберігає один авторитетний набір даних; графові алгоритми працюють локально; узгоджується з поточними SRS і C4. | RAM-модель потрібно відновлювати та підтримувати узгодженою. Вона споживає пам’ять і CPU API та ускладнює майбутнє масштабування на кілька процесів. **Обрано.** |

Порівняння є архітектурним: воно не підміняє бенчмарк альтернатив на однаковому стенді.

### 3. Decision — рішення

**Використовувати PostgreSQL 16 як джерело істини, а NetworkX DiGraph — як відновлювану обчислювальну проєкцію всередині одного процесу Backend API.**

Рішення застосовується так:

1. **Зберігання.** PostgreSQL зберігає вимоги, зв’язки, ревізії та аудит. Application Services працюють через repository-порти й Unit of Work; NetworkX приховано за IGraphEngine.
2. **Відновлення.** Під час запуску граф будується з узгодженого знімка PostgreSQL. До завершення побудови й перевірки DAG endpoint готовності не повертає успіх.
3. **Конкурентні зміни.** Усі зміни топології проходять через один прикладний сценарій. Для проєкту серіалізуються перевірка, запис і заміна RAM-проєкції. У транзакції блокується запис проєкту та читається актуальна топологія; кандидат перевіряється алгоритмом Кана. Самої наявності одного процесу недостатньо для усунення гонок.
4. **Фіксація.** Зміна, ревізія й аудит зберігаються в одній транзакції. До commit кандидат не стає загальнодоступним RAM-станом. Після commit атомарно підміняється графовий знімок, а потім публікується WebSocket-подія. Rollback відкидає кандидат.
5. **Збої.** Якщо оновлення RAM після commit не вдалося, готовність знімається до відновлення проєкції. Помилка WebSocket-розсилки не скасовує збережені дані; клієнт після перепідключення отримує актуальний стан.

Обходи виконуються над стабільним знімком: змінювати граф під час ітерації топологічного впорядкування не допускається [3].

**Інженерне обґрунтування:** рішення використовує вже прийняте сховище, не додає окремої графової СУБД і зберігає чітке розділення постійних даних та обчислювальної проєкції. Локальний обхід не потребує мережевого звернення на кожний крок; завантаження, перевірка актуальності та збереження все одно звертаються до БД.

Redis залишається залежністю для Rate Limiting. Синхронізація кількох RAM-графів через Pub/Sub у поточний варіант не входить.

### 4. Consequences — наслідки та компроміси

**Позитивні наслідки:**

- Вимоги, зв’язки, ревізії й аудит мають одне авторитетне сховище.
- Графові обчислення інтегровані з Python-сценаріями через окремий контракт.
- Не додається Neo4j-сервіс із власними налаштуваннями, оновленнями та перевірками доступності.
- RAM-граф можна відновити без збереження його як другого джерела істини.

**Негативні наслідки та їх опрацювання:**

| Ризик / витрата | Прийнятий компроміс |
| --- | --- |
| Холодний старт | Граф завантажується заново; до готовності трафік не приймається. Час відновлення вимірюється окремо. |
| Додаткова пам’ять | NetworkX зберігає Python-структури; під час перевірки можуть одночасно існувати поточний і кандидатний знімки. Вимірюється пікова RSS усього процесу. |
| CPU API та затримки інших запитів | Синхронні обчислення потребують навантажувальної перевірки. Async-драйвер БД сам по собі не прискорює графові алгоритми. |
| Серіалізація змін проєкту | Захищає DAG від конкурентного утворення циклу, але може зменшувати пропускну здатність запису. |
| Один процес API | Спрощує узгодженість, але обмежує масштабування й залишається точкою відмови. Показник доступності 99,9% перевіряється моніторингом, а не доводиться цим ADR. |
| Перехід на кілька процесів | Потребує нового рішення про версії проєкцій, виявлення пропусків і відновлення. Redis Pub/Sub сам по собі не забезпечує гарантованого відтворення пропущених повідомлень [5]. |
| Залежність від NetworkX | Порт IGraphEngine зменшує зв’язність, проте заміна бібліотеки потребує перевірки результатів і продуктивності. |

**FinOps:** відсутність додаткової графової СУБД зменшує кількість компонентів експлуатації, але не доводить конкретної грошової економії. Порівняння витрат має враховувати CPU, пікову RAM, зберігання, резервні копії та супровід усієї конфігурації. Суму в гривнях або доларах без тарифу та фактичного профілю не встановлено.

### 5. Перевірка рішення та умови перегляду

| Перевірка | Очікуваний результат |
| --- | --- |
| **Pytest: цикл і конкуренція.** До A→B→C додати C→A; окремо одночасно додати A→B і B→A до порожнього графа. | Цикл відхилено; обидва протилежні ребра одночасно не збережені; PostgreSQL і RAM містять узгоджений DAG. |
| **Pytest: відновлення.** Перезапустити API після збереження графа; окремо змоделювати збій RAM-оновлення після commit. | Стан відновлено з PostgreSQL; до відновлення готовність негативна; підтверджені дані не втрачені. |
| **PERF-02.** 10 прогрівальних і 100 вимірюваних повних впорядкувань DAG із 10000 вузлів і 30000 ребер. | p95 < 50 мс; генератор результату повністю вичитується, кожний порядок перевіряється. Завантаження з БД не вимірюється цим тестом. |
| **PERF-01.** k6: 2 хв прогрівання та 15 хв при 500 RPS; 70% читання вимоги, 20% списку, 10% редагування. | За профілем SRS p95 TTFB кожної операції < 150 мс, помилок < 1%, пропущених ітерацій немає. Клієнтські IP дотримуються Rate Limiting. |
| **Ресурси й відновлення.** Зафіксувати пікову RSS, CPU та час готовності після запуску. | Отримано відтворюваний звіт із версіями ПЗ, конфігурацією стенда й розміром даних. Не оголошено неузгодженого ліміту RAM або часу старту. |

Наведено **критерії перевірки**, а не результати виконаних тестів. Статус Approved стосується архітектурного вибору.

ADR переглядається, якщо потрібні кілька API-процесів або безперервне обслуговування при відмові процесу; якщо змінюється розмір/щільність графа; або якщо вимоги продуктивності не виконуються після профілювання. Нове рішення повинно містити порівняльні вимірювання.
