# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ПОСТАНОВКА ЗАДАЧІ ДОСЛІДЖЕННЯ

## 1.1. Інженерний опис існуючих систем-аналогів

Для обґрунтування доцільності розробки системи UseTrace Studio було проведено системний аналіз трьох програмних продуктів-аналогів, що застосовуються в індустрії для управління вимогами та архітектурного моделювання:

1. **Enterprise Architect (Sparx Systems)** — класична настільна CASE-система.
2. **Jama Connect** — корпоративна веб-платформа для управління вимогами та трасувальністю (Traceability).
3. **ReqView** — локально-орієнтований (Local-First) інструмент управління специфікаціями у парадигмі Docs-as-Code.

### 1. Enterprise Architect (Sparx Systems)

* **Архітектурний патерн та масштабованість:** Продукт реалізовано на базі дволанкового патерну Fat Client / Desktop Monolith (C++/MFC) з можливістю розширення до триланкової схеми через проміжний шлюз Sparx Pro Cloud Server (PCS). Уся обчислювальна бізнес-логіка, валідація UML-метамоделей, генерація коду та розрахунок топології діаграм виконуються безпосередньо в процесі на боці робочої станції користувача. Можливості горизонтального масштабування клієнтського рівня відсутні. При збільшенні обсягу моделей (понад $10^5$ елементів) виникає деградація мережевого каналу через вибірку великих масивів реляційних даних для подальшого парсингу клієнтським застосунком.
* **Протоколи передачі даних та взаємодії:** Застосовуються прямі інтерфейси підключення до СУБД (ODBC, OLE DB, ADO), шлюз Pro Cloud Server Gateway (HTTP/HTTPS, JSON/XML) та REST API на основі специфікації OSLC (Open Services for Lifecycle Collaboration). Підтримка асинхронного дуплексного стримінгу стану (WebSockets, gRPC) відсутня; оновлення графа вимог вимагає ручного перезавантаження або синхронного опитування (polling).
* **Базовий стек даних та консистентність:** Зберігання здійснюється у файлових СУБД (SQLite, MS Access/EAPX) або централізованих реляційних СУБД (PostgreSQL, Microsoft SQL Server, Oracle, MySQL). Забезпечується строгий рівень транзакційності ACID. Застосовується песимістичне або оптимістичне блокування пакетів (таблиця `t_secpolicies`, атрибути Package Locking), що обмежує паралельний запис з інших сесій до обраного піддерева моделей.
* **Критичні інженерні недоліки (Technical Bottlenecks):** Реляційна схема даних (системні таблиці `t_object`, `t_connector`, `t_diagram`), спроєктована для стандартних RDBMS, не оптимізована для обходу графових структур, що призводить до падіння продуктивності ($I/O$ bottlenecks) при виконанні складних JOIN-запитів та рекурсивних CTE. Відсутні математичні алгоритми синхронізації (Operational Transformation або CRDT), а песимістичне блокування створює блокуючі затори при паралельній розробці в команді понад 10–15 аналітиків. Завантаження щільних графових моделей викликає значний витік оперативної пам'яті (Client Memory Footprint).

### 2. Jama Connect

* **Архітектурний патерн та масштабованість:** Систему побудовано за багатошаровою веб-архітектурою Enterprise Web Application (JVM, Spring Framework) із подієво-орієнтованими компонентами (Event-Driven Integration). Безстатусні (stateless) веб-сервери піддаються горизонтальному масштабуванню під керуванням Kubernetes/ALB. Проте центральна СУБД та підсистема пошуку стають вузьким місцем під час масового імпорту артефактів або пакетного оновлення зв'язків.
* **Протоколи передачі даних та взаємодії:** Зовнішня взаємодія здійснюється через RESTful API (HTTP/HTTPS, JSON), а внутрішньосервісна — через асинхронні брокери повідомлень (Apache Kafka, RabbitMQ, ActiveMQ). Для зовнішніх подій застосовуються Webhooks. Потокова реактивність обмежена; основний обмін даними здійснюється за схемою Request-Response.
* **Базовий стек даних та консистентність:** Первинним сховищем (Source of Truth) є реляційні СУБД (PostgreSQL, Microsoft SQL Server). Вторинне сховище — Elasticsearch / Apache Lucene (NoSQL / Inverted Index) для прискорення повнотекстового пошуку та побудови матриць трасуваності. Застосовується модель Hybrid Consistency: ACID для первинного запису в СУБД та Eventual Consistency для асинхронного відображення оновлених пошукових індексів.
* **Критичні інженерні недоліки (Technical Bottlenecks):** Спостерігається затримка синхронізації індексів (Indexing Latency Lag) при виконанні пакетних операцій (понад $10^4$ вимог), що створює розсинхронізацію між PostgreSQL та Elasticsearch. Відзначається висока обчислювальна складність рекурсивного обходу дерев вимог при глибині зв'язків $N \ge 5$, високі накладні витрати серіалізації REST API (JSON) та висока ресурсомісткість серверного середовища виконання JVM (high infrastructure overhead).

### 3. ReqView

* **Архітектурний патерн та масштабованість:** Продукт спроєктовано як Local-First / Offline-First Desktop Application на базі кросплатформеного фреймворку Electron (Node.js із нативними C++ модулями). Командна співпраця реалізується через децентралізовану синхронізацію файлових артефактів у системах контролю версій (Git, SVN). Серверна інфраструктура відсутня, а масштабованість за кількістю паралельних редакторів обмежена механікою злиття гілок.
* **Протоколи передачі даних та взаємодії:** Використовується локальне введення-виведення (стиснені JSON/XML проєктні архіви), SSH/HTTPS для взаємодії з Git/SVN репозиторіями, а також інтерфейс CLI та локальний REST API. Мережеві сокети WebSockets/gRPC для обміну дельтами змін у реальному часі відсутні.
* **Базовий стек даних та консистентність:** Застосовується In-Memory Document Store. Граф вимог повністю завантажується в оперативну пам'яті процесу (In-Memory DOM structure) та періодично скидається на диск у вигляді ієрархічних JSON-структур. Класичний транзакційний ACID-двигун відсутній; консистентність у межах сеансу забезпечується однопотоковим Event Loop Node.js/C++. Конфлікти паралельної розробки вирішуються за допомогою Git 3-way merge або механізму Document Locking.
* **Критичні інженерні недоліки (Technical Bottlenecks):** Наявні апаратні обмеження оперативної пам'яті (Memory-Bound Scaling) та паузи Garbage Collector (GC) двигуна V8 при роботі з великими специфікаціями. Через збереження у монолітних JSON-файлах паралельне редагування викликає нерозв'язні Git merge-конфлікти на рівні сирого тексту. Відсутність обробки потокових дельт (CRDT/OT) унеможливлює реактивне сумісне редагування (live-editing), а локальні обчислення графів призводять до затискання головного потоку виконання (UI Thread lock).

### Аналітичний висновок підрозділу 1.2

Проведений критичний аналіз архітектурних рішень систем-аналогів (Enterprise Architect, Jama Connect, ReqView) виявив низку фундаментальних інженерних обмежень, які унеможливлюють ефективне сумісне моделювання вимог у сучасних розподілених командах. Застосування застарілого патерну «Fat-Client Desktop Monolith» у поєднанні з реляційними схемами даних, не оптимізованими під графові структури, призводить до високої затримки (latency) при складних рекурсивних вибірках та жорстко обмежує паралельну розробку через песимістичне блокування пакетів. Автономні Electron-рішення з локальним утриманням моделей у пам'яті (In-Memory DOM Store) стикаються з критичними апаратними бар'єрами (Memory-Bound Scaling), блокуваннями головного потоку виконання (UI Thread lock) та паузами збирача сміття (Garbage Collector), а відсутність атомарних блокувань викликає нерозв'язні текстові конфлікти при Git-синхронізації. Своєю чергою, навіть важковагові веб-платформи на базі JVM з гібридною моделлю консистентності (PostgreSQL + Elasticsearch) порушують цілісність відображення трасуваності через часову затримку асинхронної індексації (Indexing Latency Lag). При цьому повна відсутність дуплексних реактивних протоколів у всіх аналогах унеможливлює наскрізну двосторонню синхронізацію моделей та верифікаційного беклогу в режимі реального часу.

Для усунення визначених системних дефектів у розроблюваній веб-системі «UseTrace Studio» передбачено реалізацію Clean Architecture у поєднанні з мікросервісною веб-архітектурою, що чітко розмежовує обчислювальні контексти. Застосування асинхронного ASGI-фреймворку FastAPI гарантує високу пропускну спроможність та неблокуюче введення-виведення (Non-blocking I/O) при мінімальних інфраструктурних витратах. Винесення обчислень топології вимог, оцінки трудовитрат та трасувальних зв'язків у локальний In-Memory DAG-двигун на основі бібліотеки NetworkX дозволяє виконувати алгоритми обходу орієнтованих ациклічних графів із часовою складністю $O(V+E)$, знімаючи рекурсивне обчислювальне навантаження з реляційного сховища PostgreSQL (SQLAlchemy v2 + asyncpg). Впровадження дуплексного протоколу WebSockets забезпечує двосторонню синхронізацію стану між клієнтом та сервером без затримок синхронного опитування (polling), тоді як використання Mermaid.js переносить процеси рендерингу UML-діаграм на сторону клієнта (Vue 3) шляхом трансляції легковагового DSL-коду.

Таким чином, результати порівняльного аналізу доводять недоцільність запозичення архітектурних шаблонів розглянутих продуктів та повністю обґрунтовують технічну необхідність розробки програмного комплексу «UseTrace Studio». Обраний технологічний стек створює оптимальний баланс між строгою транзакційною консистентністю даних (ACID) та високопродуктивним обробленням графових моделей у реальному часі. Отримані висновки та сформульовані технічні вимоги є безпосереднім підґрунтям для Розділу 2 («Проєктування»), у якому буде розроблено контейнерні та компонентні архітектурні моделі системи (C4 Model), визначено специфікацію REST/WebSocket API, а також спроєктовано ER-діаграму бази даних і структуру DAG-обчислень.

## 1.3. Аналіз та порівняння існуючих рішень на ринку готових програмних продуктів

Проведено системний порівняльний аналіз трьох провідних індустріальних аналогів: **Enterprise Architect (Sparx Systems)**, **Jama Connect** та **ReqView**.

За результатами аналізу визначено, що наявні ринкові рішення розпадаються на три ізольовані технологічні категорії, кожна з яких має нездоланні архітектурні дефекти при застосуванні у сучасних Agile/DevOps процесах:

1. **Десктопні моноліти (Enterprise Architect):** Орієнтовані на песимістичне блокування пакетів даних у базі, що унеможливлює паралельну роботу команд чисельністю понад 10 аналітиків.
2. **Важковагові Enterprise-платформи (Jama Connect):** Застосовують дублювання сховищ (PostgreSQL + Elasticsearch), що викликає часовий лаг індексації та тимчасову розсинхронізацію матриць трасуваності.
3. **Local-First / Docs-as-Code утиліти (ReqView):** Обмежені апаратним обсягом RAM пристрою користувача та генерують Git merge-конфлікти на рівні текстових JSON-структур.

Жоден із наявних аналогів не забезпечує одночасно оперативної обробки графа вимог у пам'яті з часовою складністю $O(V+E)$, реактивної двосторонньої синхронізації з UML-діаграмами через DSL-коди та автоматичної перевірки правила 8/40 для WBS-декомпозиції.

## 1.4. Аналіз обраної предметної області в межах дослідження (модель As-Is)

### 1.4.1. Загальна характеристика домену та тенденції розвитку

Предметною областю дослідження є **інженерія вимог (Requirements Engineering, RE)** та **управління життєвим циклом додатків (Application Lifecycle Management, ALM)** у системній та програмній інженерії. Домен охоплює процеси вилучення, формалізації, трасування, верифікації та підтримки цілісності специфікацій на всіх етапах розробки програмного забезпечення. Основною метою функціонування систем у цьому домені є забезпечення суворої консистентності між концептуальними бізнес-ідеями, текстовими специфікаціями, візуальними UML-моделями, кодом та верифікаційними тест-кейсами.

Станом на 2026 рік у домені інженерії вимог зафіксовано такі ключові індустріальні тренди:
* **Перехід до парадигми Docs-as-Code:** Відмова від закритих пропрієтарних бінарних форматів та важковагових документальних файлів (`.docx`, `.vsdx`) на користь версіонованих текстових специфікацій (Markdown, DSL-коди) у системах контролю версій (Git).
* **Оперативні графові обчислення (In-Memory Graph Processing):** Перенесення обчислень топології вимог та каскадного аналізу покриття з реляційних СУБД в оперативну пам'ять сервера у вигляді орієнтованих ациклічних графів (DAG), що усуває обчислювальні затримки при обробці складних залежностей.
* **Реактивна сумісна розробка (Real-time Live-Editing):** Перехід від беч-обробки та синхронного опитування (polling) до дуплексного WebSocket-стримінгу дельта-змін у реальному часі між розподіленими членами команди.
* **Автоматизований синтез візуальних моделей:** Автоматична двостороння трансляція між текстовими специфікаціями та UML/SysML-діаграмами на основі декларативних графічних мов (Mermaid.js, PlantUML).

### 1.4.2. Ключові актори та сутності системи

В межах досліджуваної предметної області визначено 5 основних системних акторів (ролей користувачів) та 6 канонічних інформаційних сутностей.

#### Ключові актори (System Roles):
1. **Системний / Бізнес-аналітик (System/Business Analyst):** Формулює бізнес- та функціональні вимоги, встановлює зв'язки трасуваності між ними, здійснює декомпозицію специфікацій.
2. **Архітектор програмного забезпечення (Software Architect):** Валідує здійснюваність вимог, будує UML-діаграми, визначає системні компоненти та фіксує нефункціональні обмеження (NFRs).
3. **Інженер з розробки (Software Engineer):** Отримує деталізовані завдання WBS, реалізує функціональність відповідно до DSL-моделей та специфікацій.
4. **Інженер із забезпечення якості (QA Engineer):** Створює верифікаційний беклог (тест-кейси, чек-лісти) на основі графа вимог та перевіряє матрицю покриття (Traceability Matrix).
5. **Менеджер проєкту (Project Manager):** Моніторить показники оцінки трудовитрат (WBS), аналізує ризики впливу змін та контролює загальний прогрес розробки.

#### Основні сутності даних (Core Entities):
* **`Project` (Проєкт):** Корневий агрегат, що об'єднує версії специфікацій, конфігурації трасуваності та права доступу.
* **`Requirement` (Вимога):** Інформаційний об'єкт специфікації (унікальний ідентифікатор, заголовок, текстовий опис, тип, статус, версія, атрибути).
* **`TraceabilityLink` (Зв'язок трасуваності):** Орієнтоване ребро графа, що зв'язує две вимоги або вимогу з тестом (типи: *satisfies*, *verifies*, *derives*, *refines*).
* **`DAGNode / DAGEdge` (Вузол та ребро графа):** Легковагове представлення сутностей в оперативній пам'яті для швидкого обчислення топології та виявлення циклів.
* **`VerificationTask` (Верифікаційне завдання):** Елемент тестового беклогу, автоматично згенерований для перевірки конкретної вимоги.
* **`WBSEstimate` (Оцінка WBS):** Об'єкт декомпозиції робіт із зафіксованими оцінками трудомісткості в людино-годинах за правилом 8/40.

### 1.4.3. Опис бізнес-процесів та Workflows (As-Is) та їхні технічні Bottlenecks

Дослідження поточного стану бізнес-процесів (As-Is) у наявних системах-аналогах (Enterprise Architect, Jama Connect, ReqView) дозволило виділити 3 ключові процеси та локалізувати їхні технічні вузькі місця:

1. **Процес аналізу впливу змін у специфікації (Change Impact Analysis Workflow):**
   * *Перебіг процесу (As-Is):* При внесенні змін до вищої вимоги аналітик повинен визначити всі залежні елементи специфікації. У наявних системах це виконується шляхом ручного перегляду матриці або запусків рекурсивних SQL-запитів до реляційної СУБД.
   * *Технічний Bottleneck:* Використання рекурсивних SQL-запитів (`WITH RECURSIVE` або складених `JOIN` у реляційних таблицях) створює обчислювальне затискання ($I/O$ bottlenecks та $CPU$ spikes) на рівні бази даних. При обсязі графа понад $10^4$ вузлів затримка відгуку ($Latency$) перевищує 2.5 секунди, що призводить до затискання транзакцій та пропуску залежностей при передачі змін у розробку.
2. **Процес синхронізації текстових вимог із UML-діаграмами:**
   * *Перебіг процесу (As-Is):* Після коригування тексту вимоги архітектор змушений вручну відкривати графічний редактор, знаходити відповідний блок на UML-діаграмі та вручну перемальовувати зв'язки.
   * *Технічний Bottleneck:* Відсутність автоматичного зв'язку викликає «архітектурний дрейф» (*Architectural Drift*) — стан, коли текстова специфікація та візуальна модель розходяться у часі. Це призводить до виникнення помилок при імплементації коду розробниками та унеможливлює автоматичну верифікацію моделей.
3. **Процес декомпозиції вимог у WBS та формування беклогу тестування:**
   * *Перебіг процесу (As-Is):* Керівник проєкту та QA-інженер вручну переношують вимоги у баг-трекери чи електронні таблиці (Excel, Jira), розраховують трудовитрати та формують тестові сценарії.
   * *Технічний Bottleneck:* Відсутність автоматизованого контролю правила «8/40» (згідно з яким завдання WBS не повинно бути менше 8 або більше 40 людино-годин) призводить до появи некоректно декомпонованих задач у беклозі. Крім того, відсутність автоматичного аналізу покриття залишає частину вимог без верифікаційних тестів.

### 1.4.4. Регуляторні та індустріальні обмеження

При проєктуванні та розробці системи UseTrace Studio враховуються наступні нормативні стандарти та технічні регламенти:

1. **ISO/IEC/IEEE 29148:2018 (Systems and software engineering — Life cycle processes — Requirements engineering):** Стандарт регламентує класифікацію, атрибути та критерії якості вимог (недвозначність, несуперечливість, простежуваність, верифіковуваність).
2. **GDPR (General Data Protection Regulation):** Вимога забезпечення концепції *Privacy by Design*. Передбачає сувору анонімізацію та псевдонімізацію персональних даних користувачів і розробників у журналах аудиту (Audit Logs).
3. **OWASP Top 10 (2026):** Вимоги до безпеки REST API та WebSocket-з'єднань: перевірка авторизації на рівні окремих об'єктів (BOLA/IDOR), захист від Injection-атак при обробці та трансляції DSL-коду Mermaid.js, валідація корисного навантаження через JSON Schema та захист JWT-токенів (RS256).

## 1.5. ПОСТАНОВКА ЗАДАЧІ ТА ФОРМУВАННЯ ВИМОГ (МОДЕЛЬ TO-BE, CORE FEATURES, NFRS)

### 1.5.1. Концептуальна модель цільового стану процесів (To-Be)

Концептуальна модель То-Ве передбачає впровадження асинхронної веб-платформи «UseTrace Studio», яка усуває локалізовані системні дефекти та обчислювальні затискання ($bottlenecks$) шляхом розділення обчислювальних контекстів:

1. **Ліквідація затримок обходу графа ($Latency > 2.5\text{ с} \rightarrow < 50\text{ мс}$):** Обчислення топології вимог, перевірка циклів (Kahn's Algorithm / DFS) та аналіз покриття виносяться з реляційної СУБД в оперативну пам’ять сервера у вигляді орієнтованого ациклічного графа `NetworkX DiGraph`. Це знижує часову складність обходу залежностей з $O(V^2)$ до $O(V+E)$ та знімає рекурсивне навантаження з реляційного сховища.
2. **Усунення архітектурного дрейфу ($Architectural\ Drift$):** Впровадження реактивного графічного рушія на основі Mermaid.js DSL забезпечує автоматичне двостороннє оновлення між текстом специфікацій та візуальними UML-моделями у режимі реального часу.
3. **Автоматизація WBS та верифікації:** Впровадження алгоритмів калькуляції трудовитрат за суворим інженерним правилом «8/40» та автоматичного синтезу верифікаційного беклогу для QA-інженерів на основі аналізу непокритих вузлів графа.
4. **Дуплексна реактивна співпраця:** Застосування протоколу WebSockets для асинхронної трансляції дельта-змін між клієнтами без затримок синхронного опитування ($polling$) та без $Git\ merge$-конфліктів.

### 1.5.2. Функціональні вимоги (Core Features)

У системі UseTrace Studio передбачено реалізацію таких базових функціональних модулів:

#### Модуль управління вимогами та графом трасуваності:
1. **Забезпечувати** виконання CRUD-операцій над вимогами з автоматичною індексацією атрибутів, версіонуванням та валідацією за стандартом ISO/IEC/IEEE 29148:2018.
2. **Формувати** та динамічно оновлювати орієнтований ациклічний граф залежностей (DAG) між вимогами різних рівнів вкладеності.

#### Модуль аналізу впливу змін (Change Impact Analysis Engine):
3. **Виконувати** автоматичний каскадний обхід графа у пам’яті (In-Memory DAG) при модифікації вимоги та підсвічувати всі залежні сутності, що потрапляють у зону ризику.

#### Модуль реактивної UML-генерації:
4. **Транслювати** граф вимог у декларативний DSL-код Mermaid.js та здійснювати двосторонню синхронізацію між текстовим описом та візуальною UML-діаграмою.

#### Модуль оцінки WBS та верифікаційного беклогу:
5. **Розраховувати** оцінку трудовитрат у людино-годинах за декомпозиційною моделлю WBS із автоматичною валідацією правила 8/40.
6. **Генерувати** структурований беклог верифікаційних завдань (тест-кейсів) для QA-інженерів на основі аналізу матриці покриття.

#### Модуль колаборації та безпеки:
7. **Транслювати** дельта-зміни специфікації іншим підключеним користувачам у реальному часі через дуплексний протокол WebSockets.
8. **Забезпечувати** рольове розмежування доступу (RBAC) та анонімізацію персональних даних у журналах аудиту.

Для розв'язання виявлених системних дефектів обґрунтовано концептуальну модель цільового стану процесів (To-Be) та сформовано інженерні вимоги до розроблюваної веб-системи «UseTrace Studio». Доведено доцільність побудови платформи на основі асинхронного ASGI-фреймворку FastAPI та дуплексного протоколу WebSockets, що забезпечує неблокуюче введення-виведення даних та реактивну синхронізацію дельта-змін у реальному часі без Git merge-конфліктів. Для персистентного зберігання канонічних даних із гарантією ACID обрано СУБД PostgreSQL 16 (SQLAlchemy v2 / asyncpg), а рендеринг UML-діаграм реалізовано шляхом реактивної трансляції DSL-коду Mermaid.js на стороні Vue 3 SPA-клієнта.

Сформований комплекс функціональних вимог (Core Features) та чисельно вимірюваних нефункціональних метрик (NFRs: Latency p95 < 150 мс при 500 RPS, авторизація OAuth 2.0 / OIDC із JWT RS256, комплаєнс OWASP Top 10 (2026) та GDPR, контейнеризація Docker, Uptime 99.9%) є вичерпною аналітичною основою для наступних етапів дипломного проєктування. Результати аналізу предметної області, формалізована модель To-Be та специфіковані технічні вимоги стануть предметом поглибленої архітектурної деталізації (розробка моделей C4 Context/Container/Component, ER-діаграми бази даних, розробка OpenAPI та AsyncAPI специфікацій) у Розділі 2 («Проєктування») та практичної програмної імплементації й інструментального тестування у Розділі 3 («Реалізація»).
