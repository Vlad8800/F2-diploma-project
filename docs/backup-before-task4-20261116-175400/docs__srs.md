# SOFTWARE REQUIREMENTS SPECIFICATION (SRS)

**Проєкт:** UseTrace Studio
**Стандарт-орієнтир:** ISO/IEC/IEEE 29148:2018
**Спеціальність:** 121 / F2 «Інженерія програмного забезпечення»
**Дата редакції:** 14.11.2026

## 1. System Context (Контекст системи та межі)

UseTrace Studio — вебплатформа для керування вимогами, аналізу їхніх залежностей, роботи з UML-моделями, планування WBS та формування верифікаційного беклогу.

**Межі поточної SRS:** керування вимогами та їхніми версіями; побудова DAG і аналіз впливу змін; генерація та зворотне редагування UML у підтримуваному форматі Mermaid; розрахунки WBS; визначення тестового покриття; WebSocket-синхронізація.

**Користувачі:** системні аналітики, архітектори, розробники, QA-інженери та проєктні менеджери.

**Технологічний стек:** Vue 3, FastAPI / Uvicorn, PostgreSQL, NetworkX, Redis, Mermaid.js. NetworkX використовується як бібліотека всередині Backend API. PostgreSQL є постійним сховищем; RAM-граф відновлюється з нього після перезапуску.

**Зовнішні взаємодії:**

- користувачі працюють через Vue 3 SPA;
- SPA звертається до Backend API через HTTPS REST API та WSS;
- зовнішній OIDC-провайдер забезпечує автентифікацію;
- Markdown/DSL-файли зберігаються в Git у межах Docs-as-Code;
- GitHub Actions або GitLab CI запускає перевірки документації та коду.

Ця SRS уточнює наведений лабораторний обсяг. Інші модулі загальної концепції диплома потребують власних вимог перед включенням до цього приймального обсягу.

**Спільні правила для перевірки вимог:**

- Вимога містить ID, назву, текст, тип, статус і номер версії. Назва має довжину 1–200 символів, текст — 1–10000 символів; обидва поля обов’язкові. Тип: функціональна або нефункціональна. Статус: чернетка, затверджена або архівна. Некоректні дані відхиляються без часткового запису.
- Початкова версія дорівнює 1; кожна успішна зміна збільшує її на 1. Конфлікт версій повертає HTTP 409 без перезапису актуальних даних.
- Ребро A → B означає, що зміна A може вплинути на B. Архівні вимоги не входять до активного DAG. Самопетлі та ребра між різними проєктами заборонені; перевірка циклів і прийняття ребра виконуються як одна узгоджена операція.
- DAG залежностей і UML-модель є пов’язаними представленнями, але DAG сам по собі не визначає повну UML-модель. Для двостороннього редагування підтримується Mermaid `classDiagram`: класи зі стабільними ID, їхні назви, атрибути та спрямовані асоціації. Непідтримуваний або синтаксично некоректний DSL відхиляється без зміни моделі.
- Для WBS трудомісткість E задається в людино-годинах. Правило 8/40 означає допустиму оцінку кінцевого пакета від 8 до 40 людино-годин включно; вихід за межі позначається для перегляду декомпозиції. Це правило не є формулою автоматичної оцінки.
- Планова тривалість одного пакета для одного виконавця: **D = E / (8 × 0,625) = E / 5** робочих днів. Наприклад, E = 20 людино-годин дає D = 4 дні.
- Покритою вважається вимога, пов’язана хоча б з одним активним тест-кейсом. QA-завдання містить ID вимоги, її версію, назву та статус. Повторна генерація не дублює відкрите завдання для тієї самої вимоги та версії.
- WebSocket-подія містить ID події, ID проєкту, ID сутності, номер версії та змінені поля. Після перепідключення клієнт отримує актуальний стан із сервера.

## 3. Non-Functional Requirements (Нефункціональні вимоги)

| Ідентифікатор | Категорія | Вимірювана вимога |
| --- | --- | --- |
| <a id="srs-nfr-perf-01"></a>**SRS-NFR-PERF-01** | API Latency | p95 TTFB REST API має становити < 150 мс при 500 RPS за умов навантажувального профілю, визначеного нижче. |
| <a id="srs-nfr-perf-02"></a>**SRS-NFR-PERF-02** | Обробка графа | p95 часу повного топологічного впорядкування DAG у RAM повинен становити < 50 мс для 10000 вузлів і 30000 ребер. |
| <a id="srs-nfr-sec-01"></a>**SRS-NFR-SEC-01** | Автентифікація та доступ | Система повинна дозволяти захищені операції лише користувачам із валідним access token RS256, отриманим через OAuth 2.0 / OIDC, та правом доступу до відповідного проєкту. |
| <a id="srs-nfr-sec-02"></a>**SRS-NFR-SEC-02** | Rate Limiting | Система повинна приймати не більше 100 REST API-запитів за рухоме вікно 60 секунд від однієї клієнтської IP-адреси; перевищення повертає HTTP 429. |
| <a id="srs-nfr-comp-01"></a>**SRS-NFR-COMP-01** | Захист даних аудиту | Прикладні журнали аудиту повинні зберігати лише час, псевдонімний ID автора, ID проєкту, ID сутності, дію та результат; email, телефон, IP, токени, паролі й тексти вимог до журналу не записуються. |
| <a id="srs-nfr-rel-01"></a>**SRS-NFR-REL-01** | Доступність | Доступність REST API повинна становити не менше 99,9% за 30 послідовних діб безперервної експлуатації стенда. |

**Умови вимірювання продуктивності:** стенд — 4 vCPU, 8 GiB RAM, SSD; один процес FastAPI, PostgreSQL і Redis. Генератор навантаження працює окремо. У звіті фіксуються версії ПЗ та конфігурація стенда.

Для PERF-01: 2 хвилини прогрівання, потім 15 хвилин при 500 RPS; суміш запитів — 70% читання окремої вимоги, 20% списку з 50 вимог, 10% редагування різних вимог. Дані: 10000 активних вимог і 30000 ребер. p95 перевіряється окремо для кожної операції. Частка помилок має бути < 1%; пропущені ітерації генератора не допускаються. Час отримання токенів у цей профіль не входить.

Щоб 500 RPS не суперечили ліміту 100 req/min/IP, навантаження розподіляється між контрольованими клієнтськими IP з дотриманням ліміту кожної адреси. Тест з однієї IP не підтверджує цей профіль. Довільна підміна forwarding-заголовка не повинна обходити limiter.

Для PERF-02: після 10 прогрівальних виконань вимірюються 100 повних топологічних впорядкувань одного контрольного DAG. Завантаження з БД, REST-запит і рендеринг до цього часу не входять.

Для REL-01: зовнішня HTTP-перевірка готовності виконується кожні 30 секунд із timeout 5 секунд. Успішна проба — HTTP 200 за доступності БД і відновленого графа. Доступність оцінюється як частка успішних проб за повне вікно без пропусків моніторингу. Для 30 діб часовий бюджет недоступності 0,1% становить 43 хвилини 12 секунд; дискретні проби дають наближену оцінку.

Наведені показники є цілями приймання, а не вже отриманими результатами. Політика журналювання конкретизує мінімізацію даних; псевдонімізація сама по собі не означає повної анонімізації або доведеної відповідності всім вимогам GDPR.

## 4. Verification Criteria (Критерії верифікації)

| Вимога | Дія перевірки та інструмент | Очікуваний результат |
| --- | --- | --- |
| **SRS-FUN-01** | Pytest: створити валідну вимогу; окремо передати порожню назву або текст. | Валідний запис створено з унікальним ID і версією 1; некоректний запит відхилено, дані не записано. |
| **SRS-FUN-02** | Pytest: створити вимогу та двічі змінити її. | Історія містить ревізії 1, 2, 3 з відповідним вмістом; попередні ревізії незмінні. |
| **SRS-FUN-03** | Pytest: побудувати граф для A, B, C, D зі зв’язками A→B, A→C, C→D; повторити після перезапуску. | В обох випадках отримано рівно 4 вузли та 3 задані ребра без циклів. |
| **SRS-FUN-04** | Pytest: до A→B→C додати C→A; перевірити самопетлю та одночасне додавання A→B і B→A до порожнього графа. | Цикл і самопетля відхилені; одночасно обидва протилежні ребра не приймаються; збережений граф залишається ациклічним. |
| **SRS-FUN-05** | Pytest: змінити A у графі A→B, A→C, C→D з ізольованим E. | Позначку перегляду отримують лише B, C, D; їхній текст не змінюється. |
| **SRS-FUN-06** | Згенерувати DSL для двох UML-класів з атрибутами й асоціацією; перевірити через `mermaid.parse()` і відкрити у SPA. | DSL синтаксично валідний; діаграма відображається та містить задані елементи й зв’язок. |
| **SRS-FUN-07** | Pytest: перевірити E=7, 8, 20, 40, 41 та розрахунок D. | 7 і 41 позначені для перегляду; 8 і 40 допустимі; для E=20 отримано D=4 робочі дні. |
| **SRS-FUN-08** | Pytest: A має активний тест, B і C не мають; двічі запустити генерацію беклогу. | Створено по одному відкритому QA-завданню для B і C; для A завдання через відсутність покриття не створено; дублів немає. |
| **SRS-FUN-09** | Асинхронний Pytest: підключити дві сесії одного проєкту та сесію іншого; виконати зміну й перепідключення. | Підтверджену подію отримує лише дозволена сесія того самого проєкту; після перепідключення стан відповідає серверу. |
| **SRS-FUN-10** | Керований WebSocket-клієнт: спостерігати контрольні Ping/Pong протягом хвилини. | Ping надходять з інтервалом 15±1 секунди; клієнт відповідає Pong. |
| **SRS-FUN-11** | Pytest: прочитати наявну вимогу й відсутній ID у доступному проєкті. | Для наявної повернуто правильний стан; для відсутньої — HTTP 404. |
| **SRS-FUN-12** | Pytest: змінити вимогу з актуальною та застарілою версією. | Актуальна зміна збережена з новою версією; застаріла отримує HTTP 409 без втрати даних. |
| **SRS-FUN-13** | Pytest: архівувати вимогу та перевірити історію й активний DAG. | Статус архівний, історія збережена, вузол відсутній в активному DAG. |
| **SRS-FUN-14** | Pytest: у версії 3 відновити вміст версії 1. | Створено версію 4 з відновленим вмістом; попередні версії збережено. |
| **SRS-FUN-15** | Змінити назву класу та асоціацію в підтримуваному DSL; імпортувати; окремо передати некоректний DSL. | Валідні зміни застосовано зі збереженням ID; некоректний імпорт відхилено без зміни моделі. |
| **SRS-NFR-PERF-01** | k6: виконати навантажувальний профіль із розділу 3; перевірити `http_req_waiting`, помилки та фактичний темп. | Для кожної операції p95 < 150 мс при 500 RPS; помилок < 1%; пропущених ітерацій немає. |
| **SRS-NFR-PERF-02** | Pytest-бенчмарк із монотонним таймером: 100 виконань для 10000 вузлів і 30000 ребер. | p95 < 50 мс; кожний результат містить усі вершини в коректному топологічному порядку. |
| **SRS-NFR-SEC-01** | Pytest: валідний токен; прострочений токен; неправильний підпис, issuer або audience; доступ до чужого проєкту. | Валідний дозволений запит успішний; невалідний токен дає HTTP 401; відсутність проєктних прав — HTTP 403. |
| **SRS-NFR-SEC-02** | HTTP-тест: 101 запит з однієї IP за 60 секунд; повторити з іншої IP та після звільнення вікна. | 101-й запит відхилено з HTTP 429; інша IP має окремий ліміт; після звільнення вікна запити знову приймаються. |
| **SRS-NFR-COMP-01** | Pytest: виконати успішні та помилкові операції з контрольними персональними даними й секретами; перевірити всі утворені записи аудиту. | Журнал містить лише дозволені поля; контрольні персональні дані, тексти й секрети відсутні. |
| **SRS-NFR-REL-01** | Prometheus + Blackbox Exporter: накопичити зовнішні проби готовності за повне 30-добове вікно. | Частка успішних проб ≥ 99,9%; немає непояснених пропусків моніторингу. Коротка демонстрація не підтверджує місячний показник. |

SonarQube / SonarCloud та Trivy використовуються для додаткового аналізу коду, залежностей і контейнерів. Вони не замінюють поведінкових перевірок токенів, доступу та Rate Limiting.

Результати фактичних запусків зберігаються окремо із зазначенням commit коду, стенда та дати. Цей розділ визначає план перевірки.

## 5. Glossary (Глосарій)

| Термін | Визначення |
| --- | --- |
| **DAG / In-Memory DAG** | Орієнтований граф без циклів; у цій системі його робоча копія міститься в RAM, а дані для відновлення — у PostgreSQL. |
| **Docs-as-Code** | Зберігання та перевірка текстової документації через Git і CI/CD. |
